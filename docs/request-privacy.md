# 模型请求的可选诊断：1.7.0

对象为 Claude Code 2.1.296 / Bun 1.4.3 / 官方 ARM64 musl 包，审计日期 2026-10-11。
`optional-off` 在原有上报组件控制之外，关闭模型请求里的缓存诊断和工具耗时附件。
这两项随正常模型请求发送，封禁遥测域名不能处理它们。

## 从程序确定控制点

| 数据 | 实际链路 | 本轮控制 |
| --- | --- | --- |
| `diagnostics.previous_message_id` | 查询构造器检查独立的 `cache_diagnosis` 状态，附加前一条响应 ID 和诊断 beta | 只替换该功能对象的启用与检查；即使传入已有诊断状态也不启用，其他功能对象保留原逻辑 |
| `x-claude-code-prev-tool-durations` | 工具循环记录耗时，查询构造器读取 `options.prevToolDurations`，为普通流式请求及非流式回退写入请求头 | 在流式／完整响应两个查询入口屏蔽该属性；构造器无法读取载荷或生成这项附件 |
| 自定义配置重新加入上述数据 | `CLAUDE_CODE_EXTRA_BODY` 与 `ANTHROPIC_CUSTOM_HEADERS` 可重新提供诊断体、耗时头及诊断 beta | 启动、遥测初始化、查询入口及自定义头读取处清理这几项；使用官方相同 JSON 解析器，不改写用户配置文件 |

没有关闭提示缓存。组件对照保留其他 beta 的启用、拒绝和状态克隆，真实 CLI 接收器仍能看到
每次请求的缓存控制块。`thread.previous_message_id` 是另一条会话续接路径，未被这项策略
删除；单元检查验证自定义续接字段保留，但没有据此声称真实远程续接已经验收。

程序中的独立状态及无诊断字段的请求对照是本轮实现依据。[缓存诊断接口说明](https://platform.claude.com/docs/en/build-with-claude/cache-diagnostics)
还将 `diagnostics` 定义为主动启用额外诊断的选项，省略它不影响普通提示缓存。该文档关于
服务端记录行为的描述不是我们独立验证过的事实，也不能用来推断其他服务端记录不存在。

耗时控制保留本地计时；移除发生在模型查询构造器读取该属性之前。包装器保留原来的
Promise／异步迭代器对象、取消和清理行为、异常及其他请求参数。属性描述符复制不会触发
被移除的 getter，也不会提前读取其他惰性属性；支持冻结的输入和继承的选项。

自定义配置只在进程中修改。清理额外请求体时先复制解析结果，避免污染官方解析缓存；
无关配置及原本无效的 JSON 沿用原处理。自定义头按名称匹配，认证头与其他头保留。
官方自身会覆盖某些自定义 beta 头；我们验证的是保留其原有行为，不承诺所有自定义值均能
绕过官方规则进入最终请求。动态代码主动重写控制层或绕过受检查询入口不在覆盖证明内。

补测发现 bootstrap 客户端会在遥测初始化之前读取自定义头，因此只在模型查询入口清理还
不够。现在保留原自定义头构造器，并在它读取环境前清理；验收会检查所有已捕获请求，
防止诊断值从启动客户端旁路发送。这一发现和改动也说明只检查模型端点会漏掉真实路径。

## 对照及升级验收

用真实 CLI、独立 HOME、假 API key、合成工具结果和本地 TLS 接收器对比 1.6.0 与 1.7.0。
所有测试流量在本地终止，没有调用真实模型服务。报告仅保留字段名、计数和合成条件检查，
不公开请求体、身份值或提取出的官方源码。

| 场景 | 对照及检查 |
| --- | --- |
| 原始模式 | 保留缓存诊断、工具耗时及事件发送，作为正对照 |
| 关闭模式普通查询 | Bash、Read、3 次模型请求完成；无缓存诊断及耗时附件，事件接收数 0 |
| 完整响应入口 | 通过观察器让真实 CLI 调用原来的完整响应函数；至少调用 3 次，返回契约及工具循环正常 |
| 流式故障 | 本地接收器两次返回空事件流，实际触发非流式恢复；5 次请求均符合策略，工具任务完成 |
| 条件性环境头开启 | 合成功能开关明确打开该路径；它仍出现，说明本次没有误关共享环境／权限路径 |
| 自定义配置，原始与关闭模式 | 显式加入诊断体、耗时头和诊断 beta；包括 bootstrap 在内的捕获请求均无诊断头，温度、其他 beta 数据及自定义头保留 |

完整响应函数内部仍可能消费流式请求；它与“非流式恢复”是两种独立测试，不能混称。
普通场景每次请求仍有 3 个提示缓存控制块。身份字段、归因文本、请求分类等保留；
这些检查证明本轮改动没有删掉它们，不代表已证明所有字段都必需。

第 15 项安装验收 `privacy_requests` 包含上述 7 个场景，失败不切换当前版本。隐私档案最低
修订号为 5，共校验 37 个模块摘要；包括新增状态、功能定义、查询驱动、JSON 解析器及自定义头构造器。
它们是已检查控制点和依赖的版本约束，不是全部模块已完成审计的证明。
`optional-off` 拒绝直接回退到缺少本轮控制的 1.6.x。未知官方新版仍需复核后升级。

```bash
python tests/privacy-dataflow.py --root /完整候选版本/runtime --request-check --output /新的临时目录
python tests/privacy-smoke.py --root /完整候选版本/runtime --report /临时目录/privacy.json
node --test tests/test-request-policy.mjs
```

机器可读结果见[请求诊断证据](audits/2.1.296-request-privacy.json)。其他适配能力及既有隐私控制
继续执行完整验收，见[设备验证](device-validation.md)。

## 已识别但没有删除的部分

- 身份构造器仍附加 `device_id`、`account_uuid`、`session_id` 等关联信息。设备值来自配置里的
  随机标识；远程分支的 `tk` 追踪到轮次归因键，不能仅凭名字称它为认证 token。没有伪造或轮换身份。
- 条件性环境头仍可包含权限模式、容器、平台、仓库和运行环境类别。共享客户端还承担认证、
  路由和权限功能，不能把整个构造器直接停掉。真实账号是否获配开关以及服务端如何使用这些字段尚未验证。
- system 内的 `x-anthropic-billing-header` 归因文本仍保留。其环境退出选项在部分分支被忽略，
  因而不是通用关闭办法；占位值也不足以证明完整的后续处理。
- 普通事件调用方仍可能先计算参数才进入已关闭的事件总线。缓存分析还会在本地计算消息／工具
  摘要及调试状态，本轮没有停用其混合用途流程，也没有宣称不再进行任何本地分析。

这些是明确的后续审计对象，不能一概归为正常功能或一概当作可安全删除的数据。真实账号、
Remote Control、服务端关联与保存行为，以及 native、插件和独立工具进程的所有出口仍无完整证明。
